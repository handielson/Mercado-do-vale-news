# n8n cutover reconciliation (read-only)

Run from the `mercado-do-vale` repository on the operator workstation. The script reads the active Evolution PostgreSQL database and the API MySQL database over SSH; it never sends or replays a message. It prints counts only. Detailed WhatsApp IDs and Meta event keys go into a new ACL-restricted, Git-ignored `.local/*.private.json` file. Handle these files as customer metadata; do not attach them to tickets or commit them.

1. Immediately before pausing ingress, run `node scripts/n8n-upgrade-reconcile.cjs baseline`. Record the returned private file path. This captures the active Evolution database clock, a 120-second overlapping inbound window, existing WhatsApp IDs, the highest Meta inbox event ID, and the Meta worker activation marker.
2. Pause both ingresses using `node scripts/n8n-upgrade-ingress-control.cjs pause`, then read back with `status`. Continue with the separately verified backup, upgrade, and health checks. The API continues to persist incoming Meta webhook events while its reply worker is paused. Evolution may retain messages in its database, but disabled webhook delivery is **not** a guaranteed replay queue.
   The installed Evolution API retains URL and flags but empties the event list when its webhook is disabled. The control script verifies this exact paused shape and restores the verified URL, base64/by-events flags, and the three original event types on resume. If pause fails after changing Evolution, it checks and restores both ingresses before returning an error. Never assume a failed pause left Evolution enabled; run `status`.
3. Resume both ingresses with `node scripts/n8n-upgrade-ingress-control.cjs resume` and confirm `status`. Then run `node scripts/n8n-upgrade-reconcile.cjs reconcile "<baseline private file path>"`. Repeat reconciliation after the ingress backlog has had time to drain.
4. Stop and inspect privately if `newEvolutionWithoutBotLog`, `newMetaEventsWithoutJob`, or `newMetaJobsUnresolved` remains nonzero. The private result file distinguishes new Evolution inbound messages from preexisting overlap messages; the latter can be expected for ignored message types. A missing bot log is an audit candidate, not proof of a failed reply. Check workflow execution and human replies before deciding whether anything should be replayed. Reconciliation itself makes no changes.
   In the 2026-10-19 upgrade, two unlogged Evolution events were `reactionMessage` events. They did not contain customer text and were not replayed. Inspect event type before treating an unlogged ID as a missed conversation.

The Evolution watermark is a database epoch plus ID set, because WhatsApp IDs do not sort chronologically and message timestamps have one-second resolution. The overlap guards events near the boundary. The MySQL check matches WhatsApp IDs against inbound `n8n_bot_messages` rows. The Meta check uses monotonically increasing `meta_attendance_events.id` and left-joins `meta_attendance_jobs` by `event_key`. `completed` and `suppressed` jobs are treated as resolved; other job states stay visible for investigation. This does not prove customer-visible delivery, which must be checked separately in execution and outbox records.
