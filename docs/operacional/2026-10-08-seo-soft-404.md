# Tratamento das URLs antigas e soft 404

Diagnóstico de 08/10/2026: exportação do Search Console de 07/10 aponta
1.479 URLs afetadas e contém 1.000 exemplos. URLs inexistentes, incluindo um
arquivo em /wp-includes/ e um artigo de madeireira, retornavam HTTP 200 com
o HTML inicial do aplicativo. Categorias antigas eram redirecionadas para
/produtos sem preservar a categoria. O sitemap atual não continha nenhum
dos 1.000 exemplos por correspondência exata.

## Fontes e comportamento

- Rotas válidas: routes/index.tsx. scripts/sync-nginx-spa-routes.cjs usa o
  parser TypeScript, ignorando comentários e o catch-all, para gerar os
  blocos SPA das configurações Nginx de produção e staging. O prebuild
  verifica a sincronização; após alterar rotas, executar o gerador.
- Caminhos desconhecidos: Nginx retorna 404, preservando arquivos existentes.
- WordPress removido, tags, variações e feeds: 410.
- Categoria antiga: services/legacyCatalogSeo.cjs consulta categories na
  API oficial. Correspondência única de slug/hierarquia redireciona 301
  para /produtos?categoria=<id>. Sem correspondência, 410; falha de banco,
  503. A paginação antiga não é reaproveitada porque tamanhos e agrupamentos
  mudaram; o visitante chega à primeira página da categoria equivalente.
- Produto antigo /produto/<slug>/<id-numérico>: usa a consulta SEO existente.
  Produto encontrado redireciona 301 para sua rota atual; removido retorna
  410. O número antigo não é tratado como ID atual do banco.
- Paginação atual: a mesma lista de grupos usada na tela determina se uma
  página maior que 1 está vazia após terminar todos os lotes, sem erro.
  Apenas nesse caso Helmet marca noindex, follow. A resposta HTTP dessas
  listagens continua 200: não foi criado um contador SQL concorrente que
  poderia ignorar agrupamento, visibilidade ou filtros da tela.

## Publicação e validação

Nenhum deploy ou alteração de dados foi realizado nesta tarefa. Para ativar,
seguir a skill publish-vps e publicar frontend, módulo/entrypoints da API e
configuração Nginx juntos. Atualizar somente o frontend não corrige o status
HTTP dos caminhos inválidos. Sincronizar e instalar a configuração Nginx
também quando forem adicionadas rotas React novas.

Regressão: node --test tmp-tests/seo-soft-404.test.cjs, testes SEO/Nginx
existentes, node --check nos entrypoints e npm run build. A configuração
proposta também passou nginx -t na VPS usando arquivo temporário isolado,
sem instalar configuração ou recarregar o serviço.

Após publicar, conferir 200 nas rotas reais, 404 em caminho aleatório,
410 em /wp-includes/, categoria preservada no 301, produto antigo válido
com 301 e produto removido com 410. Conferir uma listagem válida e uma
página vazia depois de todos os lotes. Só então solicitar validação no
Search Console; a contagem depende de nova visita do Google.
